# AI Resume Optimizer 项目总结

## 1. 项目背景

AI Resume Optimizer 是一个面向求职场景的 AI 简历优化应用。项目目标是让用户输入目标岗位和原始简历内容后，通过大模型生成更适合招聘场景的简历表达，并给出修改理由和关键词建议。

这个项目适合作为 AI 应用工程师作品集项目，因为它不是单纯调用一次模型接口，而是包含了前端表单、后端 API、Prompt 设计、模型调用、结构化返回、流式输出、错误处理、安全约束、历史记录和基础测试，覆盖了一个小型 AI 应用从输入到输出的完整流程。

## 2. 技术栈

| 模块 | 技术 |
| --- | --- |
| 后端框架 | FastAPI |
| 数据校验 | Pydantic |
| AI 模型调用 | DeepSeek API, OpenAI Python SDK |
| 环境变量管理 | python-dotenv |
| 服务运行 | Uvicorn |
| 前端页面 | HTML, CSS, JavaScript |
| 前后端通信 | Fetch API, JSON |
| 流式输出 | FastAPI `StreamingResponse` |
| 本地历史记录 | JSON 文件 |
| 测试 | Python unittest, FastAPI TestClient, mock |
| 项目管理 | Git, GitHub, `.gitignore`, README, docs |

## 3. 核心功能

- 用户输入目标岗位和原始简历内容。
- 后端校验空输入和超长输入，避免无效请求继续调用 AI。
- 后端调用 DeepSeek 模型生成简历优化结果。
- 支持结构化 JSON 返回，前端分区展示优化后的简历、修改理由和关键词建议。
- 支持流式输出，用户可以逐步看到生成内容。
- 前端支持复制优化结果。
- 成功优化后保存本地历史记录到 `data/history.json`。
- 提供 `/history` 接口读取最近 10 条历史记录。
- 提供 `/health` 健康检查接口。
- 对 AI 调用失败、超时、返回为空和返回格式异常进行明确错误处理。

## 6. 遇到的问题

项目推进过程中主要遇到这些问题：

- 一开始后端逻辑集中在单个 `day06.py` 文件里，配置、接口、AI 调用、Prompt、历史记录混在一起。
- 前端字段和后端字段曾经存在不一致风险，容易导致返回结果无法正确展示。
- AI 返回内容不稳定，可能出现空内容、非 JSON、Markdown 代码块或格式不符合预期。
- 真实 AI API 不适合直接用于自动化测试，因为会消耗额度、依赖网络和真实 API Key。
- `.env`、本地历史记录和日志都有潜在隐私泄露风险。
- 用户输入没有长度限制时，可能导致成本过高、请求超时或服务性能下降。
- 历史记录保存的是用户简历优化结果，如果误提交到 GitHub，会造成隐私问题。
- 前端直接打开 `index.html` 调用本地后端时，需要处理 CORS 和错误提示。

## 7. 如何解决

针对这些问题，项目采用了以下解决方案：

- 使用 `.env` 保存真实 API Key，并通过 `.env.example` 提供配置模板。
- 在 `.gitignore` 中忽略 `.env`、虚拟环境、缓存目录和 `data/` 运行时数据。
- 将配置集中到 `config.py`，减少后端主文件中的环境变量读取逻辑。
- 将 AI 客户端调用逻辑拆分到 `services/ai_client.py`，降低 `day06.py` 的复杂度。
- 使用 Pydantic 限制输入字段长度，简历内容最大 8000 字符，目标岗位最大 100 字符。
- 对空简历做显式校验，返回清晰 JSON 错误，不调用 AI。
- 对 AI 调用失败、超时、返回为空和流式中断做统一错误处理。
- Prompt 中明确要求模型输出固定结构，结构化接口要求返回可被 `json.loads()` 解析的 JSON。
- 前端使用安全 DOM API 展示结果，避免直接拼接 HTML。
- 日志只记录请求路径、状态码、耗时、错误类型和简历长度，不记录完整简历和 API Key。
- 历史记录接口限制本机访问，降低隐私泄露风险。
- 测试中使用 mock 替代真实 AI 调用，避免依赖真实网络和真实密钥。

## 8. 项目亮点

- **业务场景明确**：简历优化是一个真实、清晰、容易理解的 AI 应用场景。
- **AI 应用闭环完整**：包含输入、校验、Prompt、模型调用、结果解析、前端展示和历史记录。
- **结构化输出能力**：通过 Prompt 和后端解析，让模型结果能稳定进入前端 UI。
- **流式交互体验**：支持 `StreamingResponse`，更接近真实 AI 产品体验。
- **安全意识较强**：API Key 不进入前端，日志不记录完整简历，运行时数据不提交 GitHub。
- **工程化逐步推进**：从单文件开始，逐步拆出 `config.py` 和 `services/ai_client.py`，避免一次性大重构。
- **可测试性设计**：基础 API 测试使用 mock，不依赖真实 AI API，适合持续迭代。
- **文档较完整**：包含 README、API 文档、后端学习笔记和项目总结，便于面试官理解项目。

## 10. 下一步升级方向

### 微信小程序

- 将当前 `index.html` 前端迁移为微信小程序页面。
- 小程序端通过 `wx.request` 调用后端 API。
- 后端需要部署到公网 HTTPS 域名，因为微信小程序不能直接调用本地地址。
- 增加小程序端的输入框、结果展示、复制按钮和历史记录页面。
- 适配移动端交互，比如字数统计、加载状态、错误提示和请求取消。

### 登录系统

- 增加用户注册和登录。
- 可以先用账号密码登录，后续接入微信登录。
- 后端增加用户身份识别，历史记录按用户隔离。
- `/history` 不再只依赖本机访问，而是根据登录用户返回对应数据。
- 增加鉴权中间件，保护简历优化接口和历史记录接口。

### 数据库

- 将 `data/history.json` 替换为数据库存储。
- 初期可以使用 SQLite，方便本地开发。
- 后续部署可以切换到 PostgreSQL 或 MySQL。
- 设计用户表、简历优化记录表、调用日志表。
- 支持按用户查询、删除历史记录、分页查看历史记录。

### 部署

- 使用云服务器、Render、Railway、Fly.io 或其他平台部署 FastAPI 后端。
- 使用环境变量配置 `DEEPSEEK_API_KEY`，不在代码仓库保存真实密钥。
- 配置 HTTPS 和正式域名，方便前端或微信小程序调用。
- 收紧 CORS，只允许正式前端域名访问。
- 增加接口限流，避免恶意请求消耗 AI API 额度。
- 增加生产日志和监控，记录请求数量、错误率和接口耗时。
- 将前端部署到静态站点平台，或者改造成小程序作为主要入口。
